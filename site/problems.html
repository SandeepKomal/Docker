Docker itself

Cannot connect to the Docker daemon

The error

Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?

Why it happens

The docker CLI found no daemon listening on the socket: dockerd is stopped or failed to start.

Likely causes

  • dockerd failed at start, often because /etc/docker/daemon.json is not valid JSON
  • The service was stopped, or never enabled after install
  • DOCKER_HOST or the current context points somewhere else

Confirm

systemctl status docker
sudo journalctl -u docker --since '10 min ago'
docker context ls

Fix

  1. Read the journal for the reason
  2. Fix it (for example the JSON in /etc/docker/daemon.json)
  3. sudo systemctl start docker

Prevent it

Validate daemon.json before restarting (python3 -m json.tool /etc/docker/daemon.json) and change it through configuration management.

permission denied on /var/run/docker.sock

The error

permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock

Why it happens

Your user may not open the Docker socket, which belongs to root and the docker group.

Likely causes

  • You are not in the docker group
  • You were added, but your shell started before that (groups load at login)

Confirm

ls -l /var/run/docker.sock
id

Fix

  1. sudo usermod -aG docker $USER
  2. newgrp docker # or log out and back in

Prevent it

Remember that the docker group is root-equivalent: grant it deliberately, or use rootless Docker. Never chmod 666 the socket.

fork: Resource temporarily unavailable

The error

fork() failed while spawning "worker process" (11: Resource temporarily unavailable)

Why it happens

The host (or a container's cgroup) has no process IDs left, so programs cannot start processes or threads.

Likely causes

  • A container leaking processes or threads with no --pids-limit
  • A fork bomb
  • A cgroup pids limit set too low for the app

Confirm

docker stats --no-stream   # PIDS column
cat /proc/sys/kernel/pid_max
docker exec <name> cat /sys/fs/cgroup/pids.max

Fix

  1. docker rm -f <leaking-container>
  2. docker run --pids-limit 200 ... to re-create it capped
  3. docker restart <affected-container>

Prevent it

Set --pids-limit (pids_limit in Compose) on every container, so one leak cannot take the host down.

Slow or timing out at a CPU limit

The error

curl: (28) Operation timed out after 5001 milliseconds with 0 bytes received

Why it happens

The container hit its CPU quota and the kernel throttles it. Nothing crashes; everything is slow.

Likely causes

  • --cpus (or a Compose cpus limit) set below the real load
  • A traffic peak beyond what the limit was sized for

Confirm

docker stats --no-stream   # CPU % pinned at the limit
docker inspect <name> --format '{{.HostConfig.NanoCpus}}'
docker exec <name> cat /sys/fs/cgroup/cpu.stat   # nr_throttled

Fix

  1. docker update --cpus 1 <name> # takes effect at once

Prevent it

Size CPU limits from measured load with headroom, and alert on throttling, not only on errors.

Container will not stay up

Exited (0) right after it starts

The error

Exited (0) 2 seconds ago

Why it happens

The main process finished without an error. A container lives exactly as long as PID 1.

Likely causes

  • The server was started as a daemon (nginx without daemon off, service x start) and returned
  • A shell with no terminal attached: docker run -d alpine runs sh, which exits at once
  • The command ends with &, so the shell exits and takes the container with it

Confirm

docker ps -a --filter name=<name>
docker inspect <name> --format '{{.Path}} {{.Args}}'
docker logs <name>

Fix

  1. Run the program in the foreground (nginx -g 'daemon off;', or the image's default CMD)
  2. docker rm <name> and run it again with that command

Prevent it

Use the image's default command when you can; never background the main process.

Exited (1) or another non-zero code

The error

Exited (1) 3 seconds ago

Why it happens

The app started and failed. The reason is almost always in its last log lines.

Likely causes

  • A dependency it cannot reach (a name that does not resolve, a database not ready)
  • Missing files: a mount over the app, a wrong WORKDIR, a missing module
  • No permission to write where it needs to
  • Missing configuration (an environment variable)

Confirm

docker logs --tail 50 <name>
docker inspect <name> --format '{{.State.ExitCode}} {{.State.Error}}'
docker inspect <name> --format '{{json .Mounts}}'

Fix

  1. Read the logs, fix the cause they name, re-create the container

Prevent it

Make apps fail with a clear message on bad configuration, and check required variables at start.

Exited (137), OOMKilled true

The error

Exited (137)

Why it happens

137 is 128 + 9: the process received SIGKILL. With OOMKilled true, the kernel killed it for passing its memory limit.

Likely causes

  • A --memory limit below what the app really uses
  • A memory leak that grows until it hits the limit
  • Without OOMKilled: docker kill, or docker stop after the 10-second grace period

Confirm

docker inspect <name> --format '{{.State.OOMKilled}} {{.HostConfig.Memory}}'
docker stats --no-stream
sudo dmesg | grep -i oom

Fix

  1. docker update --memory 512m --memory-swap 512m <name>
  2. docker start <name>

Prevent it

Size limits from measured use under load (docker stats), with headroom, and alert on restarts.

docker stop takes 10 seconds, then Exited (137)

The error

Exited (137) 1 second ago   (after docker stop)

Why it happens

The process ignored SIGTERM, so Docker waited for the grace period and sent SIGKILL. In-flight work is cut off.

Likely causes

  • The app runs as PID 1 and has no SIGTERM handler; the kernel ignores the signal
  • Shell-form CMD: /bin/sh is PID 1 and may not pass the signal on
  • A wrapper script that runs the app without exec

Confirm

time docker stop <name>
docker inspect <name> --format '{{.State.ExitCode}} {{.HostConfig.Init}}'
docker inspect <name> --format '{{.Path}} {{.Args}}'

Fix

  1. docker run --init ... (tini forwards SIGTERM)
  2. or handle SIGTERM in the app and close cleanly
  3. Use exec form, and exec in wrapper scripts

Prevent it

Test shutdown in CI: docker stop must finish well inside its timeout with exit code 0 or 143.

exec format error

The error

exec /usr/local/bin/docker-entrypoint.sh: exec format error

Why it happens

The image's binaries are for another CPU architecture than this host. The container exits with 255.

Likely causes

  • An image built on an Arm laptop (Apple silicon) run on an amd64 server, or the other way round
  • A single-platform image pushed under a tag others expect to be multi-platform

Confirm

docker image inspect <image> --format '{{.Architecture}}'
docker info --format '{{.Architecture}}'
docker buildx imagetools inspect <image>

Fix

  1. docker build --platform linux/amd64 -t <image> .
  2. or publish both: docker buildx build --platform linux/amd64,linux/arm64 --push .

Prevent it

Build release images in CI for every platform you run on.

Likely causes

exec: permission denied (entrypoint script)

The error

exec: "/app/start.sh": permission denied: unknown

Why it happens

The entrypoint exists but has no executable bit, and nobody, not even root, may execute it (exit code 126).

Likely causes

  • A script committed without +x, or created on Windows
  • COPY keeps the file's mode from the build context

Confirm

ls -l start.sh
docker run --rm --entrypoint ls <image> -l /app/start.sh

Fix

  1. chmod +x start.sh and rebuild
  2. or COPY --chmod=755 start.sh /app/ in the Dockerfile

Prevent it

Store the bit in git (git update-index --chmod=+x start.sh) and set it in the Dockerfile.

curl: (56) Connection reset by peer

The error

curl: (56) Recv failure: Connection reset by peer

Why it happens

Docker accepted the connection on the host port, but nothing answered on the container side.

Likely causes

  • -p 8080:8080 when the app listens on 80 inside
  • The app listens on 127.0.0.1 inside the container instead of 0.0.0.0

Confirm

docker port <name>
docker logs <name>   # where does the app say it listens?
docker exec <name> wget -qO- localhost:<port>

Fix

  1. Publish to the port the app uses
  2. Make the app listen on 0.0.0.0

Prevent it

Configure servers to bind 0.0.0.0 in containers; restrict exposure with -p 127.0.0.1:... instead.

The error

Error: getaddrinfo ENOTFOUND cache

Why it happens

The container cannot resolve the hostname it was given.

Likely causes

  • Both containers are on the default bridge, which has no DNS for container names
  • They are on different networks
  • The target container is stopped

  1. docker network create app-net

Prevent it

The error

Error: getaddrinfo ENOTFOUND host.docker.internal

Why it happens

Docker Desktop defines host.docker.internal; Docker Engine on Linux does not, unless asked.

Likely causes

  • Configuration written on Docker Desktop, run on a Linux server

  1. docker run --add-host=host.docker.internal:host-gateway ...
  2. or extra_hosts: ["host.docker.internal:host-gateway"] in Compose

Prevent it

Add the extra host in the compose file so it works the same everywhere.

A published port is open despite ufw

The error

0.0.0.0:5432->5432/tcp

Why it happens

Docker adds its own iptables rules for published ports, and they are evaluated before ufw's.

Likely causes

  • -p 5432:5432 publishes on every interface
  • A ufw rule cannot override Docker's DOCKER chain

Confirm

docker ps
sudo iptables -L DOCKER -n
sudo ufw status

Fix

  1. Re-create the container without -p (reach it over a network), or with -p 127.0.0.1:5432:5432

Prevent it

Publish only public services; review docker ps PORTS in security checks.

EACCES: permission denied on a mount

The error

Error: EACCES: permission denied, open '/data/uploads/.write-test'

Why it happens

The container's user may not write to the mounted folder. Ownership is checked by UID number.

Likely causes

  • The host folder belongs to root and the app runs as a non-root UID
  • The image's user does not exist on the host, so names do not match

Confirm

docker run --rm <image> id
ls -ln <folder>

Fix

  1. sudo chown -R <uid>:<gid> <folder>

Prevent it

Give images a fixed numeric UID and create host folders with that owner.

The error

chown("/var/cache/nginx/client_temp", 101) failed (1: Operation not permitted)

Why it happens

Root inside the container lacks a Linux capability it needs, usually after --cap-drop.

Likely causes

  • chown needs CHOWN; switching user needs SETUID and SETGID

  1. Add back exactly what the logs ask for: --cap-add CHOWN --cap-add SETUID --cap-add SETGID

Prevent it

Prefer images that run as non-root (nginx-unprivileged), which need no capabilities.

Image scan finds critical or high vulnerabilities

The error

✗ Detected 7 vulnerable packages with a total of 7 vulnerabilities

Why it happens

A scanner matched packages in the image against known vulnerabilities. Most come from the base image, often in packages the app never uses.

Likely causes

  • A full base image (compilers, git, imagemagick)
  • A base that was not rebuilt after fixes were published

Confirm

docker scout cves <image>
docker scout quickview <image>   # how much comes from the base

Fix

  1. Move to a slim, alpine or distroless base
  2. Rebuild to pick up fixed packages
  3. Re-scan and gate on critical and high

Prevent it

Scan in CI with an exit code, rebuild images on a schedule, and keep bases small.

docker.sock mounted into a container

The error

-v /var/run/docker.sock:/var/run/docker.sock

Why it happens

Whatever runs in that container can use the full Docker API: start a privileged container, mount the host's root, and own the host. A :ro mount does not limit API calls.

Likely causes

  • Dashboards, CI agents or log shippers given the socket for convenience

Confirm

docker inspect <name> --format '{{json .Mounts}}'
docker ps --filter volume=/var/run/docker.sock

Fix

  1. Give it a socket proxy that allows only the API calls it needs, over a network (DOCKER_HOST=tcp://socket-proxy:2375)
  2. Remove the socket mount

Prevent it

Treat socket access as root on the host: review it like any privileged access, and alert on new mounts of it.

Now learn it: break and fix it yourself in Docker socket in a container, then take Level 15 · Container security. Open in DevOps Nimbus Docker.

Images and builds

The image is far bigger than the app

The error

nimbus/shop   1.0   1.62GB

Why it happens

Some layer carries more than the app needs. Image size is the sum of every layer, and a later rm does not shrink an earlier one.

Likely causes

  • COPY . . without a .dockerignore sends .git, node_modules and logs
  • A full base image (node:22 is over 1 GB)
  • Build tools and dev dependencies shipped in the final image

Confirm

docker history <image>
docker images
docker build .   # read: transferring context

Fix

  1. Add a .dockerignore
  2. Use a slim or alpine base
  3. Build in one stage, copy only production files into the final one

Prevent it

Track image size in CI and fail on large jumps.

Now learn it: break and fix it yourself in 1.6 GB image, then take Level 05 · Small images. Open in DevOps Nimbus Docker.

Every build reinstalls dependencies

The error

 => [4/4] RUN npm ci   (never CACHED)

Why it happens

The cache for a step breaks when anything it copies changes, and every later step runs again.

Likely causes

  • COPY . . comes before the install step
  • A file that changes on every build is copied early
  • --no-cache, or the build cache was pruned

Confirm

docker build --progress=plain .   # which steps say CACHED?
docker history <image>

Fix

  1. COPY package*.json ./ then RUN npm ci, and only then COPY . .

Prevent it

Order instructions from least to most often changed; in CI, reuse cache with --cache-from.

Now learn it: break and fix it yourself in Cache busted on every change, then take Level 04 · Layers and the build cache. Open in DevOps Nimbus Docker.

Cache export is not supported for the docker driver

The error

ERROR: Cache export is not supported for the docker driver.

Why it happens

--cache-to needs a builder that can export cache, and CI runners start every job with an empty cache, so without one every step runs again.

Likely causes

  • Building in CI with the default docker driver
  • No --cache-from, or a cache nobody exported yet

Confirm

docker buildx ls
docker buildx build --progress=plain ...   # look for CACHED and importing cache manifest

Fix

  1. docker buildx create --name ci --driver docker-container --use
  2. docker buildx build --cache-from type=registry,ref=<image>:buildcache --cache-to type=registry,ref=<image>:buildcache,mode=max .

Prevent it

Export and import the cache in every pipeline (registry, or type=gha on GitHub Actions).

A secret found in an image

The error

//npm.pkg.github.com/:_authToken=...

Why it happens

A credential was copied into a layer, set with ENV, or passed as a build argument. All of these stay in the image.

Likely causes

  • COPY .npmrc or .env, even if a later step deletes it
  • ARG or ENV with a token, visible in docker history or inspect

Confirm

docker history --no-trunc <image>
docker image inspect <image> --format '{{.Config.Env}}'

Fix

  1. Revoke the token first
  2. RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
  3. docker build --secret id=npmrc,src=.npmrc .

Prevent it

Scan images for secrets in CI; keep credential files in .dockerignore.

x509: certificate signed by unknown authority

The error

tls: failed to verify certificate: x509: certificate signed by unknown authority

Why it happens

The registry's certificate was signed by a CA this machine does not trust, often a company's own CA or a TLS-inspecting proxy.

Likely causes

  • An internal registry with a private CA
  • A corporate proxy that re-signs HTTPS traffic

Confirm

docker pull <registry>/<image>
openssl s_client -connect <registry>:443 -showcerts </dev/null

Fix

  1. sudo mkdir -p /etc/docker/certs.d/<registry>
  2. sudo cp ca.crt /etc/docker/certs.d/<registry>/ca.crt
  3. or add it to the system store (update-ca-certificates) and restart Docker

Prevent it

Install the company CA with the machine image or configuration management. Never use insecure-registries to get past it.

Container logs filling the disk

The error

/var/lib/docker/containers/<id>/<id>-json.log   14G

Why it happens

The default json-file driver keeps every line forever unless told to rotate.

Likely causes

  • No max-size or max-file on the container or in daemon.json
  • A chatty app logging every request

Confirm

docker inspect <name> --format '{{.LogPath}}'
sudo du -sh /var/lib/docker/containers/*

Fix

  1. Re-create with --log-opt max-size=10m --log-opt max-file=3 (or --log-driver local)

Prevent it

Set log-opts in /etc/docker/daemon.json so every new container rotates.
